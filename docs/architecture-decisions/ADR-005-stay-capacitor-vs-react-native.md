# ADR-005: WebView(Capacitor)継続か React Native 移行か — Apple審査 4.2 を起点とした再検討

日付: 2026-06-18
ステータス: 承認済み（Capacitor 継続を再確認）
関連: ADR-004（Capacitor ハイブリッド採用）

## 背景

ADR-004 で Capacitor ハイブリッド方式を採用したが、その「影響・注意点」に挙げた
**Apple審査 Guideline 4.2 Minimum Functionality（WebViewラッパー判定でのリジェクトリスク）**
をきっかけに、「いっそ React Native に作り替えるべきか」という大きな決断を壁打ちで再検討した。

論点: **現在の Capacitor の作りに iOS ネイティブ機能を取り入れることで、4.2 リスクは回避・対策できるのか？**

## 検討で得た結論（＝この記録の主眼「どう考えたか」）

### 1. 4.2 は「技術」ではなく「体験」の審査である

- Apple は WebView/Capacitor を使っていること自体では落とさない。Capacitor 製アプリは App Store に多数存在する。
- 4.2 が見るのは「ブラウザで開けるサイトと何が違うのか」という**体験の差**だけ。
- したがって:
  - React Native に変えても、中身が「検索して投票するだけ」なら **4.2 リスクは消えない**。
  - Capacitor のままでも、ネイティブ価値があれば **4.2 は通る**。
- → **「WebView vs RN」という軸と「4.2 を通す」という軸はほぼ直交している。**
  4.2 が怖いから RN、は「UX の問題を技術スタック入れ替えで解こうとする」筋の悪い手であり効かない。

### 2. このアプリ固有の“本当の 4.2 リスク”は別の場所にある

- Apple の審査は基本「審査員ひとりが1台」で行う。
- 本アプリの核心は**複数人同期投票**（ホスト=アプリ／参加者=Web）。
  ソロで触ると「キーワード入力 → 検索 → キープ/除外 → 終わり」に見え、
  まさに「普通のグルメ検索サイトでは？」という 4.2 リジェクトの典型的な見え方になりやすい。
- **これは RN にしても解決しない真の急所。** 対策は技術ではなく
  「審査員にアプリの価値をどう体験させるか」の問題。

### 3. Capacitor のまま打てる 4.2 対策（すべてプラグインで実現可能）

| 施策                                      | 4.2 効果                       | 状態                |
| ----------------------------------------- | ------------------------------ | ------------------- |
| ハプティクス                              | 小                             | 済                  |
| スワイプ投票                              | 中                             | 済                  |
| **カメラ QR スキャン**                    | **大（明確にネイティブ機能）** | 取りやめ済 → 要復活 |
| **プッシュ通知**（投票が揃った/決定した） | **大**                         | 未（将来予定）      |
| GPS 現在地                                | 中                             | 利用中              |
| 審査用デモ導線＋Review Notes              | 大（ソロ審査対策の本命）       | 未                  |

- **誤判断の訂正**: 残タスクで QR カメラスキャンを「Universal Links が申請後でないと
  動かないから不要」として取り下げていたが、これは別物。
  Universal Links（URL からの深いリンク遷移）と、カメラで QR を読んで入室するのは無関係で、
  **カメラ QR は申請前から動くし、4.2 対策として最も分かりやすいネイティブ機能**。復活を推奨。
- **本命は Review Notes + デモセッション**: 審査員が1人でも複数人投票を体感できるよう、
  事前シードした票入りデモセッションや手順/動画を Review Notes に添える。
  4.2 は「説明と追加機能」で覆るのが定石で、フレームワーク変更で覆すものではない。

### 4. React Native が正当化される唯一の条件（＝今ではない）

- ADR-004 のエスケープ条項「ネイティブ UI そのものが差別化要因になった場合のみ再検討」に従う。今はそれに当たらない。
- RN にすると:
  - クライアントの 7〜8 割を書き直し。
  - **ホスト=RN アプリ／参加者=Web の二重コードベースが恒久化**
    （参加者はインストール不要の Web が核心なので、RN にしてもここは必ず Web に残る）。
  - それでいて **4.2 は解決しない**。
- 得るものは「ホストの UI が少しネイティブで気持ちいい」だけで、コストと釣り合わない。

## 決定

- **Capacitor 継続を再確認する。** 4.2 は技術問題ではなく
  「ソロ審査員にどう価値を見せるか」の体験・運用問題として扱う。
- 最優先で足すネイティブ価値は **①カメラ QR スキャン（誤判断で取り下げ済み → 復活）／②プッシュ通知**。
- 真の保険は **Review Notes ＋ デモセッション**で、ソロ審査でも多人数投票体験を再現させること。

## 未決の上流問い（次に詰める）

1. ホスト側に「アプリでしか得られない常駐価値」を将来持たせるか
   （通知での再来訪、履歴のローカル保存、ウィジェット等）。
   もし「ホストも実質 Web で足りる」なら、_App Store 配布自体が必要か_（PWA で十分説）に戻る価値がある。
2. App Store 配布の目的は「集客チャネル」か「体験品質」か。
   - 集客が主目的 → 4.2 を最小コストで通す方向。
   - 体験が主目的 → ネイティブ価値の作り込みに投資。
     目的によって打ち手が変わる。

## 確定スコープ（2026-06-18 追記）

**動機**: 「とにかく App Store に配布してみたい」。よって 4.2 を確実に通すことを優先する。

### 採用するネイティブ価値と優先順位（価値 ÷ 労力）

1. **ネイティブ共有シート**（`@capacitor/share`）— 最小労力・最大コスパ。
   `UIActivityViewController`（AirDrop/LINE 等）をそのまま起動。セッション招待リンク・
   決定店の共有に使う＝「リンクシェアで参加」という本筋に直結。「長押し → 共有」導線も兼ねる。
2. **カメラ QR スキャン復活** — 中労力（カメラ権限＋スキャナプラグイン）。明確なネイティブ価値。
3. **Review Notes ＋ デモセッション** — 審査通過の本命の盾。ソロ審査員に多人数投票を体感させる。
4. **プッシュ通知** — 価値は最大だが最重量（Apple Developer 登録・APNs 設定・
   `@capacitor/push-notifications`・サーバー送信実装）。**初回提出には含めず次バージョンへ。**

→ **初回提出スコープ = 上記 1〜3 の「軽量3点」**（2026-06-18 確定）。
プッシュ通知（4）は通過後の次バージョンに回す。

### QR スキャンの参加者ルートに関する確認結果

- QR が指すのは単なる URL。「読む側」は **2ルート併存**:
  - Web 参加者（大多数）: iOS 標準カメラ等 → ブラウザで開く → **Web で即入室（インストール不要）**
  - アプリ利用者: アプリ内カメラスキャナで入室
- アプリ内スキャナは純粋な追加機能であり、**参加者へのインストール強制は発生しない**。
  ビジョン（インストール不要の即入室）と両立する。

### 保留にした追加案

- **ネイティブコンテキストメニュー（Haptic Touch の浮き上がるメニュー）**: 保留。
  本物は UIKit `UIContextMenuInteraction` で WebView の HTML 要素に素直に橋渡しできず、
  Swift 自作プラグインが必要で重い。Web 製の偽物は審査員に響かず 4.2 貢献が小さい。
  「長押しで何か出す」目的は上記の共有シート起動で代替できる。本体は通過後の磨き込みフェーズへ。
